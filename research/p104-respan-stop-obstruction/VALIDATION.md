# Validation and implementation bounds

The verifier is new standard-library code. It imports no predecessor constructor,
replay engine or optimizer. The input is the exact PR6345 WORD.json.gz already
on main. The source package's mathematical and supplier claims are premises.
The live README pin identifies the question; it is not a proof dependency.

Direct normal and optimized CPython 3.12.15 runs pass with warnings treated as
errors. They generate 2,660 distinct contact witnesses, including six owned
stops, and identify 42 one-step helpers. The separate streaming checker checks
the exact full candidate set and every contact witness. Ten semantic rejection
controls and two positive toy controls run in both modes. No Python assertion
implements a proof obligation, so optimized mode retains all checks.

Registered command timings and publication-byte/history checks are recorded in
the PR body. Each registered command has a 120-second timeout. Neither local
checks nor future hosted checks constitute independent scientific acceptance.
The source's full native/caller/compiler/all-size replays are intentionally
outside this local chart obstruction and were not executed.

## Power of Ten inspection

The changed code has no recursion or unbounded search. Production inputs have
at most 26,000 events, 1,024 total fields, 2,048 frames and nine basis vectors
per frame. A frame span has at most 512 elements. Every lifetime and epoch is
created by an input event. There are at most 27,024 epochs and 52,000 contact
ends. The bounded controls use fixed-size mutations of the enumerated witness
set. The compressed and expanded word are limited to 16 MiB each. Source hashes
are checked before parsing the frozen word. Metadata and other local package
files are trusted repository inputs, not a general untrusted-data service.

Every function is under 60 physical lines. Explicit contracts check source
binding, active lifetimes, chart equalities, neighboring subspaces, complete
coverage and witness uniqueness. The certificate checker separately discovers
its candidate set. There is no generated code or dynamic import. File writes
occur only for an explicitly requested receipt outside the checkout, and errors
propagate. Normal and optimized warnings-as-errors runs provide the interpreted
language diagnostics used here; no third-party static analyzer is required.

Two language/runtime deviations are explicit.

- Rule 3, fixed allocation. CPython allocates dictionaries, tuples, arbitrary
  integers and JSON objects during replay. This is restricted to the finite
  input and witness capacities above, with one synchronous execution and no
  background tasks. The ten controls copy at most one bounded certificate at
  a time. Fixed-capacity storage would require a different runtime; a future
  untrusted service must supply a separately reviewed memory budget.
- Rule 9, indirect calls. `reject` invokes one of three explicit local functions
  for bounded semantic controls. The target set is `trace`, `certificate` and
  `check_certificate`; no external callback or runtime registration is accepted.
  The normal and optimized verifier runs execute every target. Production proof
  computation uses direct calls. If the controls are moved to a separate test
  module, remove this test-only dispatch from the production verifier.

Receipt hashes bind all package files present when the command executes. A
receipt generated before a documentation edit describes those earlier bytes;
regenerate it after edits when retaining a final publication receipt.
