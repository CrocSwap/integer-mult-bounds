## Durability fix

The new harness attaches its actual observation lists to R immediately after creation, before constructor controls or numerical calls. Consequently later exception reporting includes already matched records, and list lengths separately indicate completed returns even when dispatch counters include an unfinished call.

After each original child returns, the observer captures its actual bank, verifies every returned record, appends raw bits/hash/counts, and synchronously checkpoints the completed observations. The checkpoint serializes plain host record data, not live Tape handles. It writes a same-directory temporary file, flushes it, fsyncs the file and replaces the completed-checkpoint path atomically. The actual pointwise-product bits receive the same checkpoint treatment after matching.

The first forward's checkpoint must finish before its observer returns to parent `child()`, so the later opposite call cannot start while that forward evidence remains only in a local Python list. A later process exception or process kill therefore cannot truncate an already replaced checkpoint into partial JSON. A kill during a new checkpoint can leave the previous complete checkpoint and/or a temporary file; it does not establish that the interrupted write completed. The directory itself is not fsynced, so this review makes no power-loss persistence claim.

Checkpoint exceptions remain within the successful-return observer's existing `except BaseException` cleanup: its held return is cleared and its marker retired before propagation. Pointwise output is a parent lease and remains covered by the parent finally. A checkpoint only certifies completed matched stages; its explicit scope does not issue a whole-caller success token.
