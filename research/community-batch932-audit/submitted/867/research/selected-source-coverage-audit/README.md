# Selected-source provenance gap map (seed 97 consolidation note)

**No new kappa. No certificate change. No whole-PR approvals.**

## Question

`certificates/selected-result.json` lists 76 `source_prs` behind the selected
conditional κ = 0.001661634653669567. The central ledger
(`docs/research/pr-ledger.json`) marks many of those entries `unreviewed`,
and 17 of them appear in no disposition record at all. Is the selected
record's dependency list actually uncovered, or does the coverage live in
records outside the central ledger?

## Answer

Both. Of the 76 entries, 50 have incorporated-strength records once every
family, queue, integration and publication file is indexed. The remaining 26
split into three precisely documented groups; none of them is a silent hole:

1. **File-level vendored binding, explicitly not whole-PR approval (10 PRs).**
   #635, #645, #649, #655, #656, #659, #664, #676, #685, #699.
   `research/complex-sw4-frame8/PROVENANCE.md` pins their exact heads and
   retained bytes, and `docs/research/community-frontier741-review.md` states
   verbatim that citation there "is not whole-PR approval of all predecessor
   branches". This note adds an independent byte-level re-verification of all
   298 vendored rows (see below).
2. **Narrative credit only (3 PRs).** #653, #658, #660 are credited in the
   #741 review text (and #653/#658 in PR659's retained proof notes) with no
   file-level binding in `PROVENANCE.md` and no disposition record.
3. **Historical lineage, ledger-unreviewed (12 PRs) plus one partial.**
   #315, #361, #370, #425, #433, #445, #458, #472, #496, #505, #507, #522 sit
   at `unreviewed` in the central ledger with only queue-snapshot entries;
   #620 is `partially_reviewed` (central ledger and k492 DISPOSITIONS agree).

The full per-PR map is in `COVERAGE.md` / `COVERAGE.json`, generated by
`coverage.ps1` from the repository files, not by hand.

## Method and reproduce

Base: `f567884aeb8851b6e794af1184119a3bfbe1e631`. Windows worktree, no
Python interpreter installed, so both checks are PowerShell-only and rerun
exactly:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File research/selected-source-coverage-audit/coverage.ps1
# expected: source PRs: 76, with no record anywhere: 13, with no incorporated-strength record: 26

powershell -NoProfile -ExecutionPolicy Bypass -File research/selected-source-coverage-audit/verify-vendored.ps1
# expected: VENDORED-CHECK total=298 passed=298 failed=0
```

`coverage.ps1` indexes the central ledger, all nine audit `DISPOSITIONS.json`
files, the round-9 review ledger, the overnight dispositions, the family-588
workflow dispositions, both 20261011/20261012 review queues, the pr531 and
frontier799 integration receipts (`reviewed_heads`), the frontier799
`PUBLICATION.json` and `CONTENT-COVERAGE.json` keys. `verify-vendored.ps1`
checks, for each of the 298 `SOURCE-FILES.json` rows, (a) SHA256 of the
working-tree file against the recorded digest and (b) `git hash-object` of
the working-tree file against `git rev-parse <commit>:<upstream_path>`, so no
binary content crosses the shell.

The ten #635–#699 PROVENANCE pins did not resolve in a fresh clone; all ten
were fetched from origin by SHA and each resolves to a commit object
(`git cat-file -t` = commit for all ten, plus the main pin `17ce0c79…`).
The fetch touched only the object store (`FETCH_HEAD`), not the tree.

## What this does not establish

- No finite replay was re-run here (no Python on this machine); the
  construction's replay evidence is cited, not reproduced.
- Vendored-byte identity is not whole-PR approval, per the #741 review's
  explicit scope. Groups 2 and 3 remain open review work for the project.
- The 298-row check covers the SW4-ancestor vendoring only, not the bit
  supplier or the X4 word itself.
