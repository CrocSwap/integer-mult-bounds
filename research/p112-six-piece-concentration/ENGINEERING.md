## Power of Ten inspection

1. New code is structured and nonrecursive. All parser, source, closure, orbit
   and receipt failures raise exceptions before a PASS marker. Library JSON
   parsing can reject excessive nesting; no custom recursive traversal exists.
2. Root enumeration has6561 integer candidates plus128 half-root candidates.
   Root/label lists have120 entries. Binary dimensions are at most9, axis span
   dimension8 and small-fiber span dimension7. Annihilator enumeration checks
   exactly97,155/10,795 spaces per axis and2,667 per small fiber. The separate
   checker has exactly237,336/1,107,568 subset iterations per axis. The orbit
   loop has3,780 iterations and eight transitions each. Source loops have
   explicit finite geometric dimensions. Registered timeouts are180/300/90 seconds.
3. Managed-Python allocation is a deviation from fixed-capacity allocation.
   Each input file is bounded at262144 bytes. Geometry and matrix dimensions
   are fixed. The separate `seen` table is bounded by the finite binary spaces
   generated inside an eight-space, at most97,155 or10,795 canonical bases.
   No solver, network request, thread or child process is created by package
   commands. Scoped temporary directories own failure fixtures and remove them
   on every exit. Runtime allocations are not instrumented. A fixed-allocation
   native port would require separate implementation and validation.
4. Every new function is within60 physical lines after formatting. Parsing,
   root/label reconstruction, span enumeration, geometry and incidence have
   separate responsibilities. `CHECKS.json` records measured function lengths.
5. Explicit exception checks remain active under optimization. They enforce
   source hashes, capacities, full-axis closure, independent digests, small-fiber
   maxima, label linearity, orbit coverage, parabolic/plane inventory and the
   complete incidence budget. Tests contain semantic rejecting controls rather
   than only reproducing counts.
6. Calculations are function-local. Module-visible values are fixed configuration.
   No default replay command writes research artifacts or frozen sources. Tests
   mutate copies of labels/receipts and private fixture files only.
7. Mathematical results are consumed and compared. File/parser exceptions
   propagate, and fixture writes check their returned byte count. The primary
   compares the whole deterministic receipt. The separate algorithm compares
   qualifying closure hashes and its own complete basis-domain receipt.
8. There is no eval, generated executable code or runtime mathematical patch.
   The primary imports the fixed source module only after byte authentication.
   JSON hooks and unittest mocks are bounded library-dispatch mechanisms;
   mocks are used only in explicitly described unit controls.
9. Python exposes no explicit pointer dereferencing here. Ownership is local,
   and data structures are shallow lists, sets and dictionaries. The separate
   checker imports neither the primary nor its geometry implementation. Sharing
   the literal root convention and published certificate is deliberate, not
   mathematical implementation reuse.
10. Validation uses warning-strict ordinary/optimized Python and Ruff
    E,F,I,B,UP,RUF,PLE,PLW,S,C4,SIM plus formatting. The incompatible docstring
    policies, a blanket ban on CLI PASS output and mandatory naming of every
    literal proof constant are not enabled. No selected diagnostic is suppressed.

## Source closure and scientific limits

Only canonical-main geometry is a live external input; it appears in both
SOURCES.json and VERIFY.json. Task and selected provenance also resolve on the
canonical base. Exact predecessor proofs are self-contained, role-authenticated
archives. A fresh checkout never resolves their pending heads through cached
foreign Git objects. Direct commands also run in a Git-free committed export.

The checkout must stay stable during verification. Hashing followed by import
is not an atomic filesystem snapshot. Registered replay provides a private
bytecode-cache namespace. Cold direct verification uses an initially cache-free,
read-only export. These are source-execution controls, not proof-kernel checks.
