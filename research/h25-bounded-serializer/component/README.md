# Standalone bounded serializer component: source-only proposal

Disposition proposed by the author: **GO for independent source-feasibility review; no execution admission**. The package is an additive extraction of the previously reviewed revision 3 serializer. No package module, helper, control, decoder, compiler, scientific caller or benchmark has run during authorship. AST parsing and metadata hashing only were used. This package cannot approve itself.

The independently reviewed `bounded_serialization.py` and `serialization_controls.py` are copied byte for byte. `provenance/REVIEW-v3.json` is the exact earlier review. That review approves source conditionally on a concrete consumer and parent execution gate; it does not transfer runtime or performance approval to this package. Historical review files and proposal status strings are preserved verbatim. In particular `CONTRACT-v2.json` still says 65 controls and `SOURCE-READINESS-v3.json` still says pending source review: the governing revision 3 review and `CONTROL-SPEC.json` require exactly **70 ordered controls in each of normal and -O modes**, 140 total. The broader prose families in the old bill are not a claim that every listed variant exists in this concrete suite.

`reference.py` contains exact source excerpts for `_RUNTIME_ERROR`, `require`, `canonical`, complete historical `EXPECTED`, and `write_scientific`. `REFERENCE-EXTRACTION.json` records original line spans and excerpt hashes. Whole original source files are archived under `provenance/` for independently checkable byte and AST comparison; they are never imported. The original baseline writer still eagerly canonicalizes all three objects, compares the unchanged receipt dictionary, writes result/witness/rank in original order, and returns original serialized sizes. The original `require` comes from `native_backend.py` and uses the preserved `_RUNTIME_ERROR = RuntimeError` binding. `canonical` comes from `profile_side_verifier.py`. No native backend or scientific module is needed by the extracted serializer reference.

`component_consumer.py` provides the actual new finite consumer. Its baseline and candidate modes are separate guarded process invocations. Both construct fresh exact-schema fixture objects, derive a finite expected dictionary through the unchanged reference canonical function, and clone only the unchanged writer code into separate globals containing that finite dictionary. The module's complete historical `EXPECTED` is never changed. The candidate arm calls production `make_writer(original, reference.canonical, expected, reference.require, ...)`, requires faults to be disabled, calls the resulting `writer(root, *values)`, and requires bounded-path status. The baseline arm directly calls the unchanged writer clone and does not import candidate code. Both arms perform and pay a separate local artifact readback. Parent independent receipt/readback validation is still required.

The finite fixture deliberately has at most 2048 support rows and three rank events. It exercises concrete independent usage and batch crossing, but does not represent the complete H25 caller or establish meaningful full-workload performance. Complete original artifact receipts, eager scientific witness construction, ordered complement coverage, typed return, stdout/certificate and combined native/source sealing remain separate original-goal requirements.

Standalone dependency closure consists of these local execution sources: `component_consumer.py`, `reference.py`, `bounded_serialization.py`, `serialization_controls.py`, and `CONTROL-SPEC.json`. All imports outside that set are Python standard-library or builtin dependencies. No project scientific import, native build or parked cache dependency is needed for these finite modes. Actual supported Python/JSON callable shape, interpreter and extension binaries, loader/import path, standard-library bytes and linked binary closure still require parent custody approval before execution. This source package does not authenticate the installed runtime or arbitrary process memory.

For review, the proposed future invocation shape is `python3 -B component_consumer.py --mode controls --output FRESH_EXTERNAL_PATH`, once normally and once with `-O`; baseline/candidate use the corresponding modes with the same `--rows` selection in separate fresh paths/processes. These are descriptions, not execution instructions authorized by this package. Parent alone owns the serialized guarded command queue, operation approval, exact source/manifest/bootstrap custody, independent validation, failure accounting and resource measurements. No proposed command creates a new budget. Failures and real file evidence must be retained without retry/reroll.

`BILL.json` enumerates component and conditional complete-file costs. `SOURCE-PINS.json` freezes exact source/document/provenance bytes and modes; it must itself be authenticated from an external independent parent pin. No source-only status grants a runtime PASS, measured speed/memory gain, original-goal completion or publication qualification. The author owns no publication or PR action.
