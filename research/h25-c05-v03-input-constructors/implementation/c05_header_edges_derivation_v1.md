## Input and output contract

`extract_header_edges(data, SourceOccurrence(...))` takes immutable bytes and checks their exact declared SHA256 and size. The occurrence has an absolute logical pathname, a distinct occurrence identifier, acquisition provenance, and the exact originating search-position identity when known. Equal-byte occurrences remain distinct. An optional `is_primary_source` premise records whether GCC's primary-source `#include_next` override applies. A byte hash authenticates those supplied bytes; it does not itself authenticate their pathname, alias, originating position, ownership or observation interval. Output explicitly says so.

The extractor returns literal `include`, `include_next`, `__has_include` and `__has_include_next` requests, unsupported frontier records, and separate lexical diagnostics. Filename and directive physical line numbers are distinct when splicing separates them. Every syntactically present conditional branch is scanned without evaluating guards. This yields a potential edge superset. It asserts neither that a request executes nor that it succeeds. A `lookup_only` probe does not entail header-content consumption.

An empty unsupported frontier means that the bytes lie in the supported lexical language under the premises below. It is not a transitive-header certificate. The caller still must process every discovered selected header occurrence, including each distinct `include_next` origin; supply the exact configured search relation; resolve negative lookups and aliases; account for PCH; and meet namespace/currentness obligations.

## Supported-language theorem and premises

For a family of authenticated source occurrences, assume:

1. The exact strict-C11 GCC frontend uses the selected source's ASCII-compatible input conversion, trigraph table, phase ordering and directive recognition semantics; exact Ubuntu applied-source correspondence remains a separate obligation.
2. Initial builtin and command-line macro state introduces no file-producing operator, nonliteral include operand, pragma, or assembler construct outside the scanned input family. Relevant configured preincludes and macro inputs are independently expanded into that family.
3. Every reachable occurrence has an empty unsupported frontier, and any caller-supplied external macro replacement lists satisfy the same special-operator/paste restrictions.
4. The compiler recognizes file-producing preprocessing operations only through the source forms covered below; other toolchain phases are independently covered by their own rules.

Then every header-lookup spelling arising through a supported literal include directive or literal probe in an executed guard is among the extracted requests for its occurrence. Proof: phase 1 converts trigraphs before phase 2 removes escaped newlines, including within comments and strings. The lexical scan excludes comments, character constants and ordinary string literals from directive/operator recognition, while respecting header-name contexts. A directive name is lexed without macro expansion. Every source directive that can load a header therefore appears in the scan. Its filename is either the literal that is emitted or an explicit frontier. Both arms of every conditional are visited, so guard values cannot hide an active literal directive. Macro expansion cannot create a new preprocessing directive. A special builtin produced by macro expansion must either already occur as a literal identifier in a replacement/input token stream, in which case it is scanned, or be assembled by token pasting. Paste assessment either proves its fixed fragments cannot make any special file operator or creates an explicit frontier.

The restricted header spelling alphabet is ASCII letters, digits, underscore, dot, slash, plus and hyphen. No filename is unescaped, lexically normalized, resolved, or opened. In particular `..` and absolute names retain their literal spelling; namespace resolution belongs to the caller. Other spellings are reported explicitly. Valid UTF-8 multibyte bytes in comments and ordinary string/character literals cannot introduce ASCII syntax under the input-conversion premise; bytes outside those contexts create a frontier.

The ordinary lexical language supports block/line comments, escaped characters in ordinary strings/chars, multiline block comments inside directives, strict-C11 trigraphs, direct backslash-newline splicing, CRLF/bare-CR line endings, `#` and `%:` directives, literal includes and literal probes. Macro-computed include/probe operands, unknown directives, malformed lexical/conditional forms, relevant pragma forms, `_Pragma`, assembler tokens, non-ASCII/UCN identifiers, and GCC whitespace-before-newline splice extensions create explicit frontiers. Missing final newline is deliberately unsupported despite GCC's recovery behavior.

`#pragma once` and `#pragma GCC system_header` are supported as non-file-producing diagnostics: selected libcpp bodies change once/system-header state and do not load an extra file. Conservative traversal may visit additional skipped content. Other pragmas remain unproved rather than being assumed irrelevant. Literal `_Pragma` and assembler tokens are conservatively refused even when their actual use might only alter warnings or symbol labels. A frontier is a missing supported-language argument, not evidence that its form actually caused an omitted file read.

## Token pasting refinement

The first broad census conservatively refused every `##`, dollar identifier, pragma and conditional nesting beyond 24. It is retained unchanged in `c05_header_edges_corpus_summary_v1.json` and `c05_header_edges_corpus_v1_000.json` through `_002.json`. Its 988 forms in 145 occurrences are historical diagnostics, not a demonstrated set of file dependencies.

The refined scanner distinguishes token pasting that could synthesize a special operator from pasting whose fixed fragments make that impossible. For each contiguous paste chain in a macro definition it treats formal parameters as arbitrary fragments, including empty placemarkers, and fixed adjacent tokens as their literal spelling. It overapproximates possible concatenations by a regular expression. For every completed left paste prefix, if that expression cannot equal `_Pragma`, `__has_include`, `__has_include_next`, `asm`, `__asm` or `__asm__`, the chain is a diagnostic. Otherwise it is an unsupported potential synthesized-file-operator frontier. This analysis deliberately overapproximates actual argument validity and correlations.

For example, `__GLIBC_USE_ ## F` cannot make any listed identifier; it does not obstruct the header edge theorem. `a ## b` can. The discriminating fixture defines `CAT(a,b) a##b` and uses `CAT(__has_,include)("hidden.h")` in a guard. Removing all token-paste frontiers without an equivalent argument would miss this potential lookup. Unscanned initial macro definitions and exact builtin recognition remain premises.

GCC's default `dollars_in_ident=1` permits dollar identifiers. They cannot introduce a different ASCII special operator by themselves, so they are diagnostics rather than header-edge frontiers. The acquired package corpus includes a Fortran include with `!GCC$` forms; the corpus scan does not assert that this file is reachable in the original C11 commands.
