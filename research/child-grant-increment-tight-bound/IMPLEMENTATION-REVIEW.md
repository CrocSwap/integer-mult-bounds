## Literal execution and counting boundary

The two interpreters genuinely differ in tape representation and dispatch
implementation. Primary uses sparse dictionaries with absent cells interpreted
as BLANK. Oracle uses bounded dense lists with an explicit origin offset.
Neither calls the source Machine or Tape implementation. Both receive their
candidate instruction list through the same authenticated source emitter;
they are independent simulators, not independent end-to-end constructors.
The earlier written extraction review covers that shared dependency.

Both loops start at the emitted entry and stop when PC equals stop_pc, before
executing the wrapper HALT. Every dispatched branch, write, move and goto
increments the step total once. Branches use the scanned symbol and include
their explicit default target; writes update that scanned cell; moves update
the selected head by the recorded unit direction; gotos use the recorded PC.
Reject uses the explicit failure exception. An unexpected earlier HALT fails.
The observed step counts are therefore generated by actual instruction paths,
not by the popcount formula. The primary uses that formula only afterward to
check cumulative counts; the oracle independently observes them and tests its
finite15-prefix bound and carry costs.

The source Program validation in the emitter already enforces valid implicit
successors before JSON conversion. Oracle additionally checks these successors
in its table validator; primary's local row validator is not a standalone full
Program-validity proof. That does not leave an acceptance hole here: the
executed candidate is authenticated source emission, and an incoming retained
table is compared in full against fresh emission rather than used as an
arbitrary replacement program.

## Fixtures, endpoint observers and untouched data

Both positive fixture constructors encode temporary zero as LEFT0/RIGHT1,
then encode positive values in canonical LSB-first form. Head1 is explicit.
The active tape also contains a MARK at-1 and UNIT at4096. Growth cells used
by the declared cases are blank: the largest all-ONE carry has256 bits, so
its new RIGHT is at258, far short of4096. Sequential cases use the same
evolving tape for1024 calls rather than reloading an expected answer each time.

After execution, primary parses the actual body and compares the entire sparse
map with its independently constructed expected packet, including guards.
Oracle parses actual bits, checks a positive top ONE and RIGHT, verifies LEFT,
head and both active guards, and rejects nonblank backing outside its permitted
packet/guard positions. The dense arena covers every address needed by these
fixtures; it is not claimed as an unbounded tape implementation.

Both engines also use a genuinely separate sentinel tape, snapshot its contents
and head, and require it unchanged. Their sentinel patterns intentionally differ.
That diversity does not impede certificate equality because those private
observer patterns are not certificate rows. Actual source instructions access
only active tape0. Fixture loading, host endpoint observation and the external
repeat harness are test instrumentation, not hidden instructions charged to
the isolated increment macro or a production initializer.

Each sequential record's min/max visited bounds describe that individual call.
For example the third call has maximum1, although earlier calls reached3.
The proof's ell(k)+2 space claim is the union over the whole from-zero prefix,
not an assertion that every individual row reaches the current RIGHT marker.

## Actual semantic and parser controls

The semantic controls mutate legal instructions in the actual emitted table,
then call the respective literal execution engine:

- ZERO-write changed to ZERO leaves starting value2 unchanged rather than3.
- Carry-write changed to ONE takes starting value1 to3 rather than2.
- Final return move reversed leaves the head at-1, rejected by the head observer.
- A malformed UNIT at the initial body position reaches fail_pc in the baseline.
  Changing the entry default to the ZERO path instead rewrites it into a
  canonical1; this observes loss of the guard, not merely different table bytes.

Primary detects the first three through targeted endpoint-failure exceptions;
oracle additionally records the actual wrong values/raw head before requiring
the intended observer outcome. Both check the baseline guard's rejection PC.
They also actually run the arbitrary initial value3 and require its25 steps,
demonstrating why18 is not a per-call bound. The three internal parser controls
cover duplicate keys, floats and Boolean-as-integer. Both JSON decoders also
reject nonfinite constants. Explicit exception checks remain active under-O;
there is no assert-dependent acceptance gate or catch-all treating an unrelated
failure as a successful semantic control.
