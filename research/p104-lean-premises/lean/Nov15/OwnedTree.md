# OwnedTree.lean / OwnedTreeCheck.lean: E3-tree (parent/child chronology) as a kernel fact for #7630
Kernel-only (`decide +kernel`; no sorry, no native_decide). Axioms: propext / Classical.choice / Quot.sound (the data instances: propext, Quot.sound only). OwnedTree.lean 6 s / 2.0 GB; OwnedTreeCheck.lean 12 s / 3.05 GB (under the 3.5 GB guard; the depth-1 concrete run is capped at 4 child units for that reason). Build order: OwnedSkeleton, OwnedTreeData (generated by a script, not shipped, from the #7630 word file and a copy of the #7113 caller), OwnedTree, OwnedTreeCheck.

## What "the unit tree" is, and where the data is
- The word carries NO unit tags (events are INIT/CLEAR/MOVE with registers and charts only), so the tree is not extractable from it; it comes from the contract's execution model. FINITE-PRECOMPILATION.md section 3: "At round j, suspend every unit of that class, complete the entire child class fed by that round, and only then advance the parents". So a child unit is a COMPLETE call made at a paid round (a MOVE), atomic from the parent's view; section 6: each live unit instance has its own bank ("a different unit tag"), "the parent resumes, reads or erases its center only after the entire child unit has completed ... a clear never acts on a descendant's live storage".
- The child of a node is the same finite word (uniform supplier / self-similar recursion), so one skeleton `skel` describes every node.
- The caller layer (#7113 as a local copy, sha 255d89f3, read as data): 4,783 events, exactly 17 `J` (native call) events, all other ops in {ADD, SCALE, LAMBDA, SWAP, QUERY, IDLE_ODD, IDLE_ONE}. None of these creates or erases owned storage, so the caller owns nothing; the 17 native calls are sequential siblings (children [k]), not nested.
- Call sites: the 6,250 MOVE events of the word, each with gap = number of owned events before it (sitesAll; 47 are owned MOVEs, sitesOwned). The theorem below does not depend on which sites are calls.

## What is defined and proved
- `execU sites d p L`: run unit `p` to recursion depth `d`; at gap g run every child `p ++ [j]` with `sites[j] = g`, to completion, before event g. Banks are `(path, field)`. `applyEv`: INIT needs the bank dead, MOVE needs it live, CLEAR needs it live AND no live bank of any strict descendant (E3's clause, `desc`).
- `go_frame` (frame lemma): E1 of one unit (`e1run l es = some l'`) transports to the tagged run inside ANY context with no live bank at or below the unit; the context is restored.
- `execU_id`: from `e1run [] skel = some []` (a `decide +kernel` fact, ie E1 of `Sk skel`), by induction on depth: running any unit in a context with nothing at or below it returns the context unchanged.
- `e3_tree sites d : execU sites d [] [] = some []` for ALL depths and ALL call-site lists; `e3_tree_real` instantiates it at the real 6,250 sites (`n_sites`).
- `caller_tree sites d`: the 17 sequential native calls [0]..[16], each a depth-d tree, run from the empty state and end empty. `caller_17_calls`, `caller_alphabet`, `caller_len` (Check file).
- Concrete runs: `concrete_d1_owned` (root + first 4 real owned-MOVE sites as child units, kernel-evaluated, `some []`).
- Negative controls, all rejected (`= none`): `c_child_leak` (child leaves a bank live, parent's CLEAR rejected), `c_child_steals` (child CLEARs the parent's label under its own tag), `c_clear_with_desc` (parent CLEAR with a live descendant bank), `c_caller_leak`, `c_real_child_leak` (the real skeleton minus its last event as the child unit, called mid-parent). Accepting twins: `c_child_ok`, `c_clear_no_desc`.

## Reading of E3 (precision, no false statement found)
- E3-tree is not independent evidence: given atomic calls and unit-tagged banks, it is IMPLIED by E1's "nothing live at the end" for the child (`execU_id`), whatever the call sites. The 2,165 crossing lifetime pairs and the 251 CLEARs under a live smaller-chart field are all INSIDE one unit's own lifetimes; E3 constrains only ancestor-vs-descendant, so they are not violations. The flat word could not show this, and neither does it need to.
- Counterexample to a different reading (not the contract's): if "the tree" were a chart hierarchy (child = field on a strictly smaller chart) the flat word would violate "clear never acts on a descendant's live storage" 251 times. Nothing in the contract text identifies a unit with a chart level; section 3 identifies units with paid rounds. If a reviewer holds the chart reading, that is a real objection.
- The clause is not automatic if a compiler interleaves child rounds with parent events (non-atomic children). The contract's own section 3 forbids that, so atomicity is part of E3's wording, but it is an execution-model assumption, not a property of the word.
